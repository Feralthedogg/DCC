# DCC 2.0 Public API Redesign

## Status

Approved direction: a breaking 2.0 redesign. DCC 1.x source and binary
compatibility are not preserved. DCC 2.x starts a new compatibility baseline.

## Goal

DCC 2.0 exposes one obvious application path, one explicit runtime path, and
one REST path. It removes duplicate spellings and endpoint mirrors, makes
network completion errors observable by default, and makes every evolvable
caller-owned structure ABI-versioned.

The redesign must preserve DCC's Discord coverage and performance advantages.
It must not retain aliases merely to make 1.x code compile.

## Constraints

- The implementation language remains C11.
- LLAM 2.2.0 remains the minimum supported runtime dependency.
- The release version and shared-library ABI major become 2.0.0 and 2.
- Existing uncommitted JSON parser and benchmark changes are outside this work
  and must not be reverted or rewritten.
- All supported platforms continue to use the same public API: Linux, macOS,
  Windows, and the existing BSD package checks.
- Builders remain stack-friendly. Constructing a builder must not allocate.
- An asynchronous call must serialize or copy all borrowed request input before
  returning so block-scoped builder literals remain safe.

## Non-goals

- No new Discord endpoint coverage is added as part of the redesign.
- Gateway parsing, cache algorithms, voice codecs, and hot-reload behavior are
  unchanged unless adapting to a new public type requires a mechanical change.
- DCC 1.x compatibility headers are not shipped in the DCC 2 package.
- The redesign does not introduce a C coroutine abstraction.

## Public Header Architecture

### Bot layer

`<dcc/bot.h>` is the only recommended include for normal bot applications. It
contains a curated macro and inline-helper surface with a hard budget of 300
`DCC_` macros after preprocessing.

The header is assembled from focused, standalone headers:

- `<dcc/bot/handlers.h>`: handler declaration helpers.
- `<dcc/bot/listeners.h>`: listener descriptors.
- `<dcc/bot/replies.h>`: context response helpers.
- `<dcc/bot/ui.h>`: Components v2 application UI constructors.
- `<dcc/bot/main.h>`: development and production entry points.

`<dcc/sugar.h>` and `include/dcc/sugar/` are removed from the installed and
source public API.

### App layer

`<dcc/app.h>` aggregates only application runtime behavior:

- `<dcc/app/base.h>`: opaque types, handler types, and common descriptors.
- `<dcc/app/options.h>`: app and command-sync options.
- `<dcc/app/lifecycle.h>`: create, start, stop, wait, run, and destroy.
- `<dcc/app/listeners.h>`: listener registration and removal.
- `<dcc/app/context.h>`: interaction context access and response actions.
- `<dcc/app/modules.h>`: modules and app definitions.
- `<dcc/app/store.h>`: access to the app-owned store.

The declaration fragments `core_decls.h`, `rest_decls_a.h`, `rest_decls_b.h`,
and `context_decls.h` are removed. No public header may begin or end in the
middle of a declaration. Every installed public header must compile by itself.

App no longer mirrors the Discord REST surface. Arbitrary channel, guild,
member, webhook, and resource operations use `dcc_app_client(app)` with the
matching `dcc_rest_*` endpoint. Context-local interaction response helpers
remain because they own interaction flow state rather than duplicate REST.

### Core and REST layers

Focused Core headers remain the embedding API. `<dcc/dcc.h>` is the complete
aggregate for framework authors and includes `<dcc/bot.h>`; tutorials do not
recommend it.

`<dcc/rest.h>` and domain headers under `<dcc/rest/>` are the only public
Discord endpoint surface. Every Discord endpoint has one typed submit function,
not separate raw JSON, params, builder, callback, async, and future overloads.
Raw HTTP access remains available only through `dcc_rest_submit()`.

## Canonical Bot API

### Handler contract

All App handlers return `dcc_status_t`. The dispatcher forwards a non-OK return
to the App error handler. Void handlers and a macro that expands to bare
`return;` are removed.

```c
DCC_SLASH_FN(ping) {
    return DCC_CTX_REPLY_TEXT(ctx, "pong");
}
```

The canonical declarations are:

- `DCC_SLASH_FN`
- `DCC_AUTOCOMPLETE_FN`
- `DCC_BUTTON_FN`
- `DCC_SELECT_FN`
- `DCC_MODAL_FN`
- `DCC_EVENT_FN`
- `DCC_READY_FN`
- `DCC_MESSAGE_FN`
- `DCC_TASK_FN`

App callback typedefs for routes, events, ready notifications, messages, and
tasks also return `dcc_status_t`. Cleanup callbacks remain `void`.

### Listener contract

`DCC_LISTEN_*` is the only listener vocabulary. `DCC_ON_*`, `DCC_ROUTE_*`,
`DCC_DECORATE_*`, and direct-registration macro aliases are removed.

Simple listeners use a short form. Advanced listeners use one `*_WITH` form
and a composable configuration value instead of combinatorial suffixes.

```c
DCC_LISTEN_SLASH("ping", "Reply with pong", ping)

DCC_LISTEN_SLASH_WITH(
    "ban",
    "Ban a member",
    ban,
    DCC_ROUTE_CONFIG(
        DCC_ROUTE_PARAMS(ban_args_t, BAN_PARAMS),
        DCC_ROUTE_POLICY(
            DCC_GUILD_ONLY(),
            DCC_REQUIRE_PERMISSION(DCC_PERMISSION_BAN_MEMBERS),
            DCC_COOLDOWN_USER(1U, 1000U)
        )
    )
)
```

The underlying dynamic API is one tagged descriptor entry point:

```c
dcc_status_t dcc_app_listen(
    dcc_app_t *app,
    const dcc_listener_t *listener,
    dcc_listener_id_t *out_id
);

dcc_status_t dcc_app_unlisten(dcc_app_t *app, dcc_listener_id_t id);
```

Listener descriptors use a tagged union. Route policies, typed bindings, and
validators are nested values rather than distinct listener struct families.

### Entrypoints

Only four entry helpers remain:

- `DCC_DEV_BOT_MAIN(name, ...)`: loads dotenv and performs development command
  synchronization.
- `DCC_BOT_MAIN(name, ...)`: production-safe; never mutates commands on READY.
- `DCC_DEV_BOT_MAIN_WITH(config, ...)`: advanced development configuration.
- `DCC_BOT_MAIN_WITH(config, ...)`: advanced production configuration.

Listener arguments are flat. `DCC_SIMPLE_BOT*`, `DCC_APP_LISTENERS`, and nested
definition aliases are removed.

### Context actions

The canonical response vocabulary is:

- `DCC_CTX_REPLY*`: state-aware interaction response.
- `DCC_CTX_DEFER*`: defer an initial interaction response.
- `DCC_CTX_UPDATE*`: update the component source message.
- `DCC_CTX_FOLLOWUP*`: force a followup.
- `DCC_CTX_SEND*`: create an unrelated channel message.
- `DCC_CTX_SHOW_MODAL*`: send a modal response.
- `DCC_CTX_AUTOCOMPLETE*`: send autocomplete choices.

`RESPONSE`, `RESPOND`, `PUBLIC`, `PRIVATE`, `DONE`, `OK`, and equivalent alias
families are removed. Visibility is named `EPHEMERAL`; `PRIVATE` is not retained
as a synonym.

`dcc_ctx_reply()` remains state-aware: it sends the initial response when ready,
edits the original response after defer, and creates a followup after a completed
initial response.

## REST Execution and Result Model

### One operation per endpoint

Each endpoint takes typed endpoint input plus optional call options and returns
an optional owned request handle:

```c
dcc_status_t dcc_rest_create_message(
    dcc_client_t *client,
    dcc_snowflake_t channel_id,
    const dcc_message_builder_t *message,
    const dcc_rest_call_options_t *options,
    dcc_rest_request_t **out_request
);
```

The function validates and serializes input, owns the serialized payload, and
queues the request before returning. Its `dcc_status_t` reports local validation,
serialization, allocation, runtime-state, or queue-admission failure only.

There are no endpoint-specific `_async`, `_sync`, `_future`, `_builder`, `_text`,
`_params`, or raw-JSON variants. Convenience is supplied by typed builders and
generic request operations.

### Request handle

`dcc_rest_request_t` replaces the separate future family. The generic API is:

```c
dcc_status_t dcc_rest_request_wait(
    dcc_rest_request_t *request,
    uint32_t timeout_ms,
    const dcc_rest_result_t **out_result
);

dcc_status_t dcc_rest_request_cancel(dcc_rest_request_t *request);
uint8_t dcc_rest_request_completed(const dcc_rest_request_t *request);
void dcc_rest_request_destroy(dcc_rest_request_t *request);
```

Destroying an incomplete request requests cancellation and releases the caller's
reference; the runtime keeps its own reference until completion. A timeout does
not invalidate the handle.

When `out_request` is null, DCC owns and releases the request automatically.
When both callback and output handle are omitted, the call is fire-and-observe:
completion failures still reach the configured client/App error observer.

### Call options

```c
typedef struct dcc_rest_call_options {
    size_t size;
    uint32_t version;
    dcc_rest_priority_t priority;
    dcc_rest_result_fn callback;
    void *user_data;
} dcc_rest_call_options_t;
```

The callback runs once on DCC worker context. The result view is borrowed for
the callback. Waiting returns a result view owned by the request handle. Callers
retain a result with `dcc_rest_result_clone()` and release it with
`dcc_rest_result_free()`.

### Result contract

```c
typedef struct dcc_rest_result {
    size_t size;
    uint32_t version;
    dcc_status_t transport_status;
    uint16_t http_status;
    int32_t discord_code;
    const char *discord_message;
    const char *body;
    size_t body_len;
    uint64_t retry_after_ms;
} dcc_rest_result_t;
```

`dcc_rest_result_ok()` is true only when transport status is `DCC_OK` and HTTP
status is in the 200-299 range. `dcc_rest_result_status()` maps a transport
failure to that transport status and a non-2xx response to `DCC_ERR_DISCORD`.

### Raw escape hatch

`dcc_rest_submit()` accepts one size-versioned request description with method,
path, content type, body bytes, priority, and callback. It uses the same request
handle and result model. String-method and enum-method overloads are removed.

## App and Interaction Error Model

All structured errors use a borrowed `dcc_error_t` view:

```c
typedef enum dcc_error_origin {
    DCC_ERROR_HANDLER = 1,
    DCC_ERROR_REST,
    DCC_ERROR_GATEWAY,
    DCC_ERROR_RUNTIME
} dcc_error_origin_t;

typedef struct dcc_error {
    size_t size;
    uint32_t version;
    dcc_error_origin_t origin;
    dcc_status_t status;
    uint16_t http_status;
    int32_t discord_code;
    const char *operation;
    const char *message;
    const char *body;
    size_t body_len;
} dcc_error_t;
```

`dcc_app_error_fn` receives `dcc_app_t *`, the error view, and user data. Handler
return failures are reported before the route context is released. Asynchronous
REST transport failures and non-2xx responses are always reported. Supplying a
per-request callback does not disable the observer.

The default observer logs structured operation, transport, HTTP, and Discord
details. For a handler failure before an interaction response is queued, the
default App policy also sends one ephemeral generic error. It never exposes a
raw Discord body to end users.

## Ordered Interaction Flow

Context actions serialize their builder input immediately and append an owned
operation to an interaction-local queue. The queue preserves call order and
holds the interaction ID, application ID, token, and response state independently
of the callback-scoped `dcc_ctx_t`.

The public state distinguishes `READY`, `INITIAL_QUEUED`, `DEFERRED_QUEUED`,
`REPLIED`, `ORIGINAL_EDITED`, `FOLLOWED_UP`, and `FAILED`. A second reply queued
behind an initial reply becomes a followup only after the initial operation
completes successfully. If an earlier required operation fails, dependent queued
operations complete with `DCC_ERR_STATE` and reach the error observer.

This preserves auto-defer and removes synchronous network waits from Gateway
and App handlers.

## ABI-safe Value and Builder Types

Every caller-initialized structure consumed by DCC begins with:

```c
size_t size;
uint32_t version;
```

Every such type has an initializer and a constant initializer macro. Library
code reads only fields covered by `size` and supports version 1 of the DCC 2
layout throughout the 2.x series.

This rule applies to options, params, request descriptions, results, listener
descriptors, route policies, builders, and snapshots. Parser-owned read-only
object views are versioned separately and may only append fields.

### Message builder

`dcc_message_builder_t` gains size and version fields plus one presence bitmask.
Parallel raw-JSON and typed representations of embeds, components, mentions,
attachments, and polls are removed. Typed fields are canonical. Arbitrary raw
payloads use `dcc_rest_submit()`.

String and array members are borrowed until the builder is serialized. All REST
and context submit APIs serialize before returning.

### Components v2 builder

`dcc_component_v2_builder_t` becomes a tagged union containing only fields valid
for its component type. Shared metadata remains in the prefix; button, select,
layout, media, text input, and modal-only data live in distinct union members.
The generic bag of fields and `has_*` bytes is removed.

Explicit constructors return values and use static inline functions where
possible. Serializer validation returns a field path through the structured
error channel.

### Bot UI vocabulary

`DCC_UI_*` is the sole application-level Components v2 vocabulary. It maps to
the tagged low-level builder and covers text, rows, buttons, cards/containers,
sections, separators, media, selects, labels, text inputs, file uploads, radio
groups, and checkboxes.

`DCC_V2_*` aliases and legacy component Sugar are removed. The explicit
`dcc_component_v2_*` C functions remain the lower-level vocabulary.

## Ownership Rules

- Opaque runtime objects use `create/destroy`.
- Heap-owned data values use `clone/free`.
- Caller-owned stack values use `init/deinit` only when they own resources.
- Accessors and callbacks return borrowed `const` views unless their name says
  `clone`, `take`, or `create`.
- Every public pointer parameter and return value documents ownership and its
  validity boundary in the declaring header.
- `user_data` lifetime requirements appear beside every callback typedef.

## Removed 1.x Surface

The following categories are absent from DCC 2 public headers and public symbol
manifest:

- `<dcc/sugar.h>` and all `include/dcc/sugar/` headers.
- `DCC_ON_*`, `DCC_ROUTE_*`, and `DCC_DECORATE_*` listener families.
- `DCC_RESPOND*`, `DCC_PUBLIC*`, `DCC_PRIVATE*`, `DCC_DONE*`, and equivalent
  context response aliases.
- `DCC_SIMPLE_BOT*`, `DCC_APP_LISTENERS`, Cog aliases, and duplicate feature and
  module spellings.
- `DCC_V2_*` and legacy component Sugar aliases.
- Endpoint-mirroring `dcc_app_*` REST functions.
- Endpoint-specific raw JSON, params, builder, text, callback, future, and
  multipart overload matrices.
- `dcc_rest_request*` string/enum overload families and `dcc_rest_future_t`.
- Public declaration fragments under `include/dcc/app/`.

Internal implementation helpers may keep similar behavior but must use internal
headers without `DCC_API` and must not appear in the installed API manifest.

## Documentation and Migration

All README, website, examples, generated projects, presets, and command-line
tool output use `<dcc/bot.h>` and only canonical names. No primary documentation
shows a removed alias.

The API reference is generated per public header from declaration comments.
The public API audit rejects an undocumented `DCC_API` declaration or public
Bot macro. The monolithic catalog sections in `docs/api.md` become task-oriented
links to generated symbol reference pages.

`docs/migration-1-to-2.md` contains a mechanical mapping table and explains
semantic changes in handlers, REST completion, request ownership, builders,
and App REST removal. `tools/dcc_migrate_v2.py` rewrites unambiguous include and
macro renames and reports constructs that require manual migration. It never
rewrites user logic silently when two 1.x forms map to different 2.0 behavior.

## Tests and Release Gates

Development follows test-first cycles. The following gates are required:

1. Each installed public header compiles alone as C11 and C++.
2. `<dcc/bot.h>` exposes no more than 300 `DCC_` macros.
3. A banned-surface audit rejects every removed alias prefix and App REST mirror.
4. A DCC 2 public symbol manifest detects removals during later 2.x releases.
5. Every public declaration and Bot macro has an ownership/behavior comment.
6. Handler tests prove returned errors reach the App error handler.
7. A delayed HTTP server proves typed REST submission returns before the server
   responds.
8. REST tests cover transport failure, 2xx, Discord 4xx with code/message, 5xx,
   cancellation, timeout, request destruction while active, callback borrowing,
   and result cloning.
9. Interaction-flow tests cover initial reply, defer/edit, multiple followups,
   ordered completion, auto-defer races, and dependent-operation failure.
10. ABI tests compile historical DCC 2 prefix layouts and verify appended fields
    are gated by `size`.
11. Builder tests cover every tagged component type and reject invalid field
    combinations before network submission.
12. Every example and generated preset compiles with warnings treated as errors.
13. Documentation code blocks used as examples are compile-tested.
14. The complete CTest suite, ASan/UBSan suite, package smoke tests, and existing
    performance benchmarks pass.

## Acceptance Criteria

The redesign is complete when:

- The project and package version are 2.0.0 with ABI major 2.
- Normal bot examples include only `<dcc/bot.h>`.
- A minimal development bot is one handler plus one flat listener declaration.
- No documented happy path discards a returned status.
- No REST non-2xx completion can disappear merely because a callback was omitted.
- App handlers perform no blocking network I/O through canonical APIs.
- App no longer exposes a duplicate Discord endpoint surface.
- The macro, banned-name, standalone-header, documentation, and ABI audits pass.
- The full supported test and packaging matrix passes without changing LLAM's
  minimum below or above 2.2.0.

## Implementation Boundaries

The work is implemented and reviewed in five independently testable boundaries:

1. Public header topology, version 2 manifest, and canonical Bot/App descriptors.
2. Status-returning handlers and centralized structured error delivery.
3. Asynchronous REST request handles, results, and ordered interaction actions.
4. ABI-versioned message and Components v2 builders plus `DCC_UI_*` constructors.
5. Removal audits, source/example/generator migration, documentation, packaging,
   and final verification.

Each boundary must leave the repository building and its targeted tests passing.
