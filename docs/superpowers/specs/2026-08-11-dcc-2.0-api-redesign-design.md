# DCC 2.0 Public API Redesign

## Status and authority

DCC 2.0 is an intentional source/ABI break. DCC 1.x compatibility is not
shipped, and 2.0.0 establishes the new same-major compatibility baseline.

Tasks 1–6 are implemented. The reviewed Task 7–15 briefs under
`.superpowers/sdd/2026-08-11-dcc-2.0-api-redesign/` are authoritative for exact
field layouts, endpoint rows, validation tables, test matrices, and commit
boundaries. This document is the cross-task contract. If an older plan snapshot
contains 231 endpoints, 60 final generic REST exports, 284 final REST exports,
a fixed 283 Bot macro count, a public flow struct, or an inline Bot runner, it
is superseded.

## Goals

DCC 2.0 provides one obvious path at each level:

- normal bots use `<dcc/bot.h>`;
- advanced runtimes use focused `<dcc/app/*.h>` APIs;
- Discord operations use one typed `dcc_rest_*` submit function per endpoint;
- unusual HTTP calls use the single raw `dcc_rest_submit()` escape hatch.

The redesign removes aliases and overload matrices, makes asynchronous
completion failures observable, preserves stack-friendly construction, and
defines an auditable same-major C ABI. Performance claims are limited to
measured DCC regressions; cross-library “fastest” claims require a separate,
equivalent public benchmark.

## Constraints and non-goals

- Production remains C11 and the public surface compiles as C11 and C++17.
- LLAM 2.2.0 is the exact minimum dependency and LLAM ABI major 2 is enforced.
- That floor is a non-cache constant (or rejects every override other than
  exactly 2.2.0), so source consumers cannot rewrite installed metadata.
- Release/package/runtime version is 2.0.0 Stable; shared ABI/SOVERSION is 2.
- Linux, macOS, Windows ClangCL, FreeBSD, OpenBSD, and NetBSD remain gated.
- Builder value construction is allocation-free.
- Every accepted asynchronous operation copies or serializes borrowed request
  data before the submit/action function returns.
- Gateway parsing, cache policy, voice codecs, and hot reload change only where
  the new public contract or a verified defect requires it.
- No C coroutine layer or DCC 1 compatibility package is introduced.

## Header architecture

### Bot

`<dcc/bot.h>` includes exactly five focused leaves:

- `<dcc/bot/handlers.h>`
- `<dcc/bot/listeners.h>`
- `<dcc/bot/replies.h>`
- `<dcc/bot/ui.h>`
- `<dcc/bot/main.h>`

`<dcc/sugar.h>` and `include/dcc/sugar/` are deleted. The Bot macro budget is
compiler-derived, not a stale hand count. Task 13 records the complete focused
dependency dump in the canonical POSIX/Clang C11 static-consumer profile, then
adds exactly 30 Bot-owned definitions: six guards, nine handler macros, two
initializer macros, nine C-only UI array macros, and four main macros. The
complete canonical C count is `dependency artifact lines + 30` and must be at
most 300; C++ omits the nine variadic UI macros. A 12-profile POSIX/Clang and
Windows/ClangCL, C/C++, static/shared-build/shared-consumer matrix prevents
platform-dependent export/deprecation expansions from being compared as if
they were one definition.

Uppercase listener/config/handler/UI/context constructors are public
`static inline` functions, not macros. They are source API and enter the same
signature/documentation baseline as lowercase inline functions.

### App

`<dcc/app.h>` aggregates exactly eight standalone headers:

- `base.h`
- `options.h`
- `lifecycle.h`
- `listeners.h`
- `context.h`
- `modules.h`
- `store.h`
- `env.h`

Public declaration fragments and `app/legacy.h` are removed. App exposes no
Discord REST mirror; callers use `dcc_app_client(app)` plus canonical REST.
Context-local response actions remain because they own interaction ordering.

`dcc_app_run_with_signals()` keeps its existing symbol and moves to
`lifecycle.h`. Environment spellings are exactly
`dcc_app_env_load_file`, `dcc_app_env_load_dotenv`, and
`dcc_app_env_validate_requirements`.

### Core and REST

Focused Core headers remain the embedding API. `<dcc/dcc.h>` is the broad
framework aggregate and includes `<dcc/bot.h>`, but tutorials recommend the
narrowest layer. `<dcc/rest.h>` and `<dcc/rest/>` are the sole endpoint surface.

## Canonical Bot API

### Handlers and listeners

All handlers return `dcc_status_t`; non-OK returns enter the structured App
error path exactly once. Cleanup callbacks remain `void`. The only handler
declaration macros are:

`DCC_SLASH_FN`, `DCC_AUTOCOMPLETE_FN`, `DCC_BUTTON_FN`, `DCC_SELECT_FN`,
`DCC_MODAL_FN`, `DCC_EVENT_FN`, `DCC_READY_FN`, `DCC_MESSAGE_FN`, and
`DCC_TASK_FN`.

There are exactly 19 listener stems and a short plus `_WITH` static-inline
function for each (38 functions total). There is no `DCC_ON_*`, `DCC_ROUTE_*`,
decorator, policy-suffix matrix, or callback cast. Advanced construction uses
one `dcc_listener_config_t`.

Listener inputs use a pointer graph that is safe for suffix evolution:

```c
typedef struct dcc_listener_config {
    size_t size;
    uint32_t version;
    void *user_data;
    dcc_app_cleanup_fn cleanup;
    const dcc_application_command_builder_t *command;
    const dcc_listener_route_policy_t *policy;
    size_t args_size;
    const dcc_listener_bindings_t *bindings;
    const dcc_listener_validators_t *validators;
    const dcc_listener_validation_policy_t *validation;
    uint8_t once;
} dcc_listener_config_t;
```

`dcc_listener_t` uses the same four child pointers and retains only its tagged
target union as the final by-value tail. `dcc_listener_route_policy_t` points
to its optional cooldown instead of embedding an evolvable child before later
fields. Middleware/check/cooldown/binding/validator/target element layouts and
the target union are frozen leaves for ABI major 2; collection/policy/listener
records may append. `dcc_app_listen()` synchronously validates and deep-copies
the descriptor graph, strings, and arrays. Callback and `user_data` pointer
values are not cloned.

`dcc_listener_init()` is a same-name public static-inline initializer, not an
exported symbol. It writes the caller-visible layout only. Null child pointers
mean empty/default configuration.

### Bot config and runner

The version-1 config is:

```c
typedef struct dcc_bot_config {
    size_t size;
    uint32_t version;
    const dcc_app_options_t *app_options;
    const char *token_env;
    uint8_t install_default_error_handler;
    uint8_t handle_signals;
} dcc_bot_config_t;
```

`DCC_BOT_CONFIG()` is a public static-inline function. There is no mandatory
unused name field. `dcc_bot_run(config, listeners, count, development)` is one
exported `DCC_API` function so same-major releases can fix orchestration. It
rejects managed callback/task entry before mutation, normalizes historical
prefixes (with null/empty `token_env` selecting `DISCORD_TOKEN`), optionally
loads dotenv only in development, resolves the token,
forces development command sync on or production sync off, registers listeners
in order, runs with the chosen signal policy, and consumes the App through
successful destruction.

After App creation, runner cleanup is intentionally blocking and never returns
while it owns a live App. User callbacks/cleanup must eventually return after
stop; violating that liveness precondition may block teardown indefinitely.
Retries wait on conditions and do not busy-spin.

The only entrypoint macros are:

- `DCC_DEV_BOT_MAIN(...)`
- `DCC_BOT_MAIN(...)`
- `DCC_DEV_BOT_MAIN_WITH(config, ...)`
- `DCC_BOT_MAIN_WITH(config, ...)`

Default forms use `DCC_BOT_CONFIG()`. Listener arguments are flat and evaluated
once. Development loads dotenv and syncs commands; production never does either
on READY.

### Context and UI vocabulary

Canonical actions are `DCC_CTX_REPLY*`, `DEFER*`, `UPDATE*`, `FOLLOWUP*`,
`SEND*`, `SHOW_MODAL*`, and `AUTOCOMPLETE*`. Visibility is `EPHEMERAL`; response,
respond, public/private, done/ok aliases are removed.

`DCC_UI_*` is the only application UI vocabulary. Exactly nine variadic array
helpers exist in C and are absent in C++; fixed and `_ARRAY` static-inline
functions work in both languages. `DCC_V2_*` and legacy component Sugar are
removed.

## REST surface and execution

### Endpoint and generic counts

- Tasks 11–13: runtime stats adds one, so 61 + 224 = 285;
- Task 14/15 cutover: 35 generic + 224 = exactly 259 final exports.

`dcc_rest_call_options_init`, `dcc_rest_request_desc_init`, and
`dcc_rest_firewall_options_init` are public static-inline functions and are not

composites, transition helpers, and App mirrors.

### One asynchronous model

Every typed endpoint takes typed input, optional call options, and optional
`dcc_rest_request_t **`. A non-OK submit return is local rejection and invokes
nobody; `DCC_OK` means accepted and guarantees exactly one terminal result.
The request handle supports cancel, wait, completed, result access, and destroy.
Callback-before-observer ordering and wait as a delivery barrier are fixed.

`dcc_rest_submit()` is the only raw HTTP entry. Endpoint-specific `_async`,
`_future`, `_params`, `_builder`, `_text`, raw JSON, multipart, callback, and
sync overload families are absent.

### Call options, authentication, and secrecy

The final version-1 call-options order is:

```c
size_t size;
uint32_t version;
dcc_rest_priority_t priority;
dcc_rest_result_fn callback;
void *user_data;
const char *audit_log_reason;
dcc_rest_auth_mode_t auth_mode;
const char *auth_token;
uint64_t flags;
```

The mandatory historical prefix ends at `user_data`. Suffix fields are read
only when fully covered. Auth modes are exactly DEFAULT, NONE, BOT, and BEARER.
Known flags are exactly
`DCC_REST_CALL_FLAG_SENSITIVE_REQUEST_BODY` and
`DCC_REST_CALL_FLAG_SENSITIVE_RESULT_BODY`; unknown covered bits are invalid.

The raw request descriptor is exactly `size, version, method, path,
content_type, body, body_len, const dcc_rest_call_options_t *options`. Null
options select defaults. A non-null options record is a separate borrowed input
validated and normalized only through `dcc_rest_submit()` return; it is never
embedded by value or retained. This removes the append-extensible-child edge
from the descriptor.

Typed endpoint policy can force sensitivity and caller flags cannot clear it.
At minimum, Add Guild Member (`access_token`), Add Group DM Recipient
(`access_token`), and Create or Join Lobby (`secret`) force sensitive request
bodies. OAuth secret-bearing forms do likewise; exchange/refresh force
sensitive results. Exact measurement/building, interceptors, retries, result
clones, observers, every retired buffer, cancellation, and teardown preserve
the effective bits and securely wipe allocated capacity.

Operation identity is always a canonical nonsecret symbol. Wire paths/URLs are
separate owned values. The exact 17 token-path endpoints force sensitive-path
handling and also force sensitive results. The exact REST sensitive-result set
is those 17 plus Create Webhook, Get Channel Webhooks, and Get Guild Webhooks
(20 total); OAuth exchange/refresh form the separate exact two-operation set.
Raw rate keys contain a full-path SHA-256 digest; token segments never
enter logs, observers, route keys, or public results.

### Results and response ergonomics

`dcc_rest_result_t` contains `size, version`, transport/HTTP/Discord status,
message/body/body length, retry delay, then `uint64_t flags`. Sensitive result
bodies remain marked through clone/free and are wiped on release. The nine
generic `dcc_rest_result_*` accessors validate the result/body prefix and parse
common scalar/object members without exposing the removed response type.

Typed requests intentionally return raw response bytes in 2.0. This keeps
network admission fast, avoids parsing data callers do not use, and makes
parsing cost explicit. Documentation must call this “typed request, raw result,”
show safe status/accessor/clone patterns, and not claim typed response models.
Post-2.0 usability work may add opt-in zero-work-when-unused decoders such as
`dcc_rest_result_decode_message/channel/...` that return owned objects, arrays,
or pages; automatic parsing is not part of 2.0.

### OAuth2

Five OAuth2 operations join the same request/result model: current
authorization, current bot application, code exchange, refresh, and revoke.
There is no OAuth callback type or synchronous `dcc_http_perform()` path.
Exchange/refresh/revoke use versioned typed form inputs. Code exchange supports
an optional presence-gated PKCE `code_verifier` (43..128 RFC-unreserved ASCII)
and treats it as secret. The helper remains a confidential-client flow with a
required client secret.

### Composite results

Command-registry apply uses its plan as the sole guild/delete-stale/dry-run
authority. Managed-message publish returns one aggregate containing composite
status, failing stage, last child REST result, new reference, storage status,
and presence. No composite retains `dcc_rest_response_t` or a private second
completion model.

## Bounded runtime resources and observability

Task 11 appends these exact zero-means-default client options:

```text
rest_max_queued_requests                 4096
rest_max_request_bytes                   32 MiB
rest_max_queued_bytes                    128 MiB
rest_max_active_bytes                    128 MiB
rest_max_response_bytes                  32 MiB
interaction_max_live_queues              1024
interaction_max_tombstones               65536
interaction_tombstone_ttl_ms             20 minutes
interaction_max_actions_per_queue        32 (active included)
interaction_max_reserved_bytes_per_queue 32 MiB
interaction_max_reserved_bytes_total     128 MiB
```

One private client ledger accounts for REST and interaction memory. Typed paths
use `validate/exact-measure -> atomic reserve -> exact build`; raw paths reserve
from explicit lengths before copying. No uncharged temporary or growth realloc
may exceed the configured hard bound. Interaction-to-REST admission moves one
payload reservation atomically and adds the REST job/handle delta; the separate
queue-node reservation stays interaction-owned through callback, observers,
post-hook unlink, and physical free. Live queue identity—including full copied
token/key and variable entry storage—is reserved before copy and held until
tombstone conversion/free. Fixed registry/tombstone arrays are checked and
preallocated from count limits. The `interaction_reserved_bytes` gauge includes
identity, nodes, and untransferred payload. There is no ownership gap or
physical double-charge. Response growth checks per-result and global active
limits before allocation.

`DCC_ERR_RESOURCE_LIMIT` is appended without renumbering existing statuses.
`dcc_rest_runtime_stats()` is the one new Task 11 generic operation. Its exact
version-1 gauges, high-water marks, completion/retry counters, REST rejection
reasons, interaction/tombstone counters, and rejection reasons are fixed by the
Task 11 brief. All values are copied from one linearizable snapshot under the
short-lived resource-accounting mutex; monotonic counters saturate.

## Ordered interaction flow

`dcc_interaction_flow_t` is opaque. Public lifecycle is
`dcc_flow_create(client, interaction, &out)` and `dcc_flow_destroy(flow)`; there
is no external init/deinit or public state field. Creation copies IDs/token.
Destroy consumes the owner while already accepted callbacks continue through
independent queue references.

Each client owns one interaction registry shared by App contexts and standalone
flows. The key is `(application_id, interaction_id, token bytes)`. Only a newly
created identity enters middleware/user dispatch. Live or completed duplicates
are suppressed before user code; public duplicate flow creation returns
`DCC_ERR_STATE`.

Every new identity reserves a future tombstone slot, preserving
`live reservations + unexpired tombstones <= max_tombstones`. Final retirement
atomically converts the slot to a tombstone containing IDs, a SHA-256 token
fingerprint, and monotonic expiry—never the raw token. Unexpired tombstones are
not evicted; full capacity rejects a new identity with
`DCC_ERR_RESOURCE_LIMIT`.

One queue mutex owns projected/committed state, original-message existence,
initial admission, timer arbitration, and FIFO topology. Only the head enters
REST. A dependent action starts only after its predecessor callback and error
observers return. First-head local rejection rolls back synchronously; accepted
terminal failure cascades deterministic local terminal results to dependents.
Auto-defer uses the same initial slot and mutex.

User callbacks run with no queue, registry, REST, observer, or accounting lock
held. App destroy detaches its registry entries, cancels/drains them, waits for
its live count, then releases observers/listeners. Client destroy closes the
common registry and standalone entries.

## ABI-safe public values

### Two extension models

Every public aggregate gets independent manifest axes:

```text
layout         opaque | fixed | size_extensible | versioned
direction      input | output | inout
lifetime       trivial | borrowed | owning | state_handle
writer_policy  none | full_fixed | covered_atomic | opaque_publish
append_policy  not_applicable | forbidden | suffix_same_layout | new_version_only
```

- Size-only records have an implicit layout generation 1 and an immutable
  historical prefix.
- Size+version records validate both fields and append only documented suffixes.
- `layout=fixed` never grows in ABI major 2, regardless of lifetime.
- Borrowed lifetime names its producer; owning lifetime names exact cleanup.
- Opaque state handles use create/destroy.
- Writer and append behavior follow their own axes; lifetime never selects ABI
  comparison rules.

Every existing record's non-layout contract is also frozen for ABI major 2:
direction, lifetime, writer/append/stride policies, initializer and empty
predicate, cleanup/consume operation, ownership anchor and minimum successful
size, required logical view/count group, ownership/producer boundary, and every
existing field's meaning and units/range. A different lifecycle requires a new
public type/API name; regenerating a baseline cannot reclassify an old record.

No externally linked ABI function passes or returns an extensible record by
value. Caller-compiled static-inline constructors may do so because no library
calling convention is involved; their signatures and record prefixes remain
frozen. An extensible child cannot be embedded before later parent fields.
Use a pointer, flatten fixed fields, or place a fixed-layout child at a frozen
tail. Arrays of extensible records require declared stride; fixed element arrays
use frozen `sizeof`.

Public allocation-free initializers are same-name static-inline functions or
constant macros so an older caller is never overrun by a newer library writing
its current `sizeof`. For the initial 1→2 reset, separately compiled synthetic
smaller-DCC2-prefix/new-library canaries—not merely a reduced `.size` in current
storage—prove bounded reads/writes. Later same-major releases also compile real
previous-Stable compat-base DCC 2 headers against the new library.

That rule applies to every public record writer, not just `_init`: setters,
parsers, builders, snapshots, resets, deinitializers, open/close, and all output
functions are classified as fixed-layout writes, caller-size/version-bounded
writes, or opaque create/open plus destroy/close. Extensible writers never use
a current-layout assignment/memset; failure is atomic, and deinitializers capture
the caller header, release private ownership, zero only covered bytes, then
restore that header.

Owning-value output producers accept only caller-initialized empty outputs.
Success requires full coverage of the manifest's ownership anchor and logical
view/count group; shorter or partial coverage fails before allocation and
leaves the value unchanged.
Populated output returns `DCC_ERR_STATE` before allocation, parsing, traversal,
or stream consumption and is bytewise unchanged; success atomically commits a
temporary. Reuse is explicit deinit plus reinitialize—no producer silently
frees or replaces an old value. Command snapshot parse, plan build, and replay-next
all test this contract, including replay no-consume rejection.

The replay record prefix is exactly `size, state, kind, ts_ms, event, payload,
payload_len`. `state == NULL` denotes borrowed recorder input; player output
uses one private owned block named by non-null `state`. Deinit never frees
borrowed bytes, frees player state once, and is idempotent. Non-null-state
records are move-only and must not be raw-copied.

Runtime state with public `size + void *state` shells becomes truly opaque.
This includes command registry, component session/store/listener, replay
recorder/player, firewall, store, and interaction flow. Creation/open publishes
`T **` only on success; destruction/close consumes the handle. The unused public
`dcc_command_registry_entry_t` is internalized. Command-registry snapshot/plan
and replay record remain bounded public owning values with caller-compiled
initializers and exact deinitializers because callers inspect their data.
All three are `layout=size_extensible`, `lifetime=owning`,
`writer_policy=covered_atomic`, and `append_policy=suffix_same_layout`;
snapshot is `direction=output`, while plan and replay record are
`direction=inout`.

Major reset is not a blanket waiver. The audit reconstructs v1.5.0 declarations,

Resolved macro expansion is compared only against the matching platform/

The regression benchmark builds recorded baseline/current sources with matching
optimization on one idle host. Each workload uses at least three warmups and 30
paired timed batches, alternating AB/BA. A sample is batch elapsed ns divided by
exact operations. Median/p95 use Hyndman-Fan type 7; CV uses sample standard
deviation and must be at most 5% after at most two full reruns. Fail median
regression over 10%, p95 over 20%, or deterministic allocation/copy growth.
Raw JSON records sample unit, pair/order, counts, hashes, environment, and the
`hf7` algorithm identifier.

Required workloads cover gateway validate/dispatch, listener dispatch at 1/32,
normal message components, Components v2, typed REST validation/serialization/
admission, and interaction FIFO/pump/drain. Sanitizers run correctness only.

## Release acceptance

DCC 2.0 is complete only when:

- all version surfaces say 2.0.0 Stable, ABI/SOVERSION 2, LLAM exactly 2.2.0;
- the exact tag is `v2.0.0` and GitHub prerelease is false;
- eight App headers, 224 endpoints, 35 generic REST exports, and 259 total REST
  exports match headers, definitions, binaries, manifests, install, and source
  archives;
- every baseline, standalone-header, documentation, banned-name, layout,
  symbol, and migration audit passes;
- normal, full sanitizer, platform, package, source archive, benchmark, and
  compile-tested documentation matrices pass from clean directories;
- no primary page claims Beta, teaches DCC 1, discards a status, promises typed
  response models, or markets DCC as the fastest Discord library without a
  separate reproducible cross-library benchmark.
