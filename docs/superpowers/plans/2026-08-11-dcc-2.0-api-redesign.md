# DCC 2.0 Public API Redesign Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Replace DCC 1.x's overlapping Sugar/App/REST API with one canonical Bot API, a focused App API, observable asynchronous REST requests, and ABI-versioned builders for DCC 2.0.

**Architecture:** Build the DCC 2 contracts beside the current implementation, migrate internals and in-tree consumers, then remove the DCC 1 public surface. The REST migration uses a checked endpoint manifest so hundreds of declarations and definitions cannot drift. Every task starts with a failing focused test and leaves its target set green.

**Tech Stack:** C11, CMake 3.20+, LLAM 2.2.0, existing DCC platform synchronization, Python 3 audit scripts, CTest, ASan/UBSan.

## Global Constraints

- Keep C11 and LLAM 2.2.0.
- Set release and shared-library ABI to 2.0.0 and 2 only in the release task.
- Do not revert or rewrite the existing uncommitted JSON parser and benchmark changes.
- Keep Linux, macOS, Windows, and BSD package checks supported.
- Builder construction performs no allocation.
- Async submission copies or serializes all borrowed input before returning.
- Do not ship a DCC 1 compatibility header in the DCC 2 package.
- The final active REST manifest is exactly 224 endpoints, partitioned
  41/35/47/57/44 across Tasks 6–10; seven unavailable candidate endpoints live
  only in a removal ledger.
- Task 7 establishes the one common audit/auth transport contract consumed by
  Tasks 8–10. Audit reasons are raw UTF-8, 1–512 Unicode scalar values, encoded
  once; per-call auth is DEFAULT/NONE/BOT/BEARER and absolute URLs receive no
  Discord credentials.

- [x] **Step 4: Implement reference-counted request state and waits**

Use one caller reference when an output handle is requested and one runtime reference while queued/active. Completion stores an owned result, signals waiters, invokes the callback once, reports errors, and drops the runtime reference. Destroy requests cancellation and drops the caller reference without blocking.

Terminal claiming must be atomic with respect to cancellation. Build the owned
result before calling user code, invoke the result callback and existing Task 3
observers without internal locks, then publish completion and wake every waiter.
Keep the runtime reference through all delivery so destroy-from-callback is
safe. Detect same-request recursive waits instead of deadlocking. The result
body is an exact owned byte span; decoded Discord metadata is owned for the
handle lifetime.

- [x] **Step 5: Implement raw submission and payload ownership**

`dcc_rest_submit()` validates the versioned descriptor and nested call options,
resolves the enum method, and copies path, content type, and exact body bytes
before queue admission. The callback/user-data pair is the only intentionally
retained borrowed input. On every local or injected admission failure, free all
copies, clear `*out_request`, and produce no terminal delivery. On success,
publish the caller reference before the worker may invoke its callback.

Always enqueue the new API, including under the synchronous test interceptor;
never execute network or interceptor work on the submitting thread. A success
from an interceptor that did not synchronously supply one valid response is a
terminal runtime failure, not a disappearing completion.

- [x] **Step 6: Implement exact per-request cancellation**

Under the existing REST lock, distinguish queued, active, terminalizing, and
completed requests. Exact cancellation publishes cancellation but keeps a
selected pending/retry-queued request owned by the queue; it must never invoke
terminal user code on the public cancel/destroy stack. When work can be
admitted, run the canceled entry through the existing runtime worker, bypassing
route, rate-limit, and retry-delay eligibility while preserving priority and
concurrency. Track whether each job actually claimed its route so a canceled
same-route worker cannot release another request's exclusion. A spawn failure
restores the exact queue position, and stopping leaves the canceled entry
queue-owned for bulk teardown. Atomically mark active cancellation and close
its exchanged fd after unlocking. Cancellation is nonblocking and idempotent;
the first terminal claimant wins. Shutdown and bulk pending cancellation may
deliver on the teardown caller, use the same handle finalizer, and release the
runtime reference exactly once.

- [x] **Step 7: Adapt the worker without changing scheduling semantics**

Connect exact body length/content type, owned result construction, callback,
observer, and runtime-reference release to the existing worker. Preserve
priority, per-route exclusion, rate-limit retries, firewall behavior, retry
wakeups, admission rollback, and shutdown drain. A transient 429 followed by
2xx has one successful completion and no transient observation; terminal 429,
transport failure, cancellation, and shutdown each complete and observe once.

Keep legacy async/future functions buildable as transition adapters until Task
14, but do not expose the new endpoint path through `dcc_rest_future_t` and do
not change its public ABI in this task.
