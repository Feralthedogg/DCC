# CLI Tools

DCC installs runtime helper tools when `DCC_BUILD_TOOLS=ON`.

## dcc_new_app

Creates a small canonical DCC 2 bot project. The default scaffold is supported
against the installed package:

```sh
dcc_new_app mybot
cd mybot
cp .env.example .env
cmake -S . -B build -DCMAKE_PREFIX_PATH="$HOME/.local"
cmake --build build
```

The generated project includes `src/main.c`, `src/ping.c`, `src/ping.h`,
`commands.json`, configuration placeholders, and a README. Its main uses
`DCC_DEV_BOT_MAIN(DCC_LISTEN_SLASH(...))`; the ping handler returns
`DCC_CTX_REPLY_TEXT(ctx, "pong")`. These are the installed canonical Bot and
listener APIs, not the old Sugar app-definition API.

Development Bot mode loads `.env`, resolves the token through the configured
token environment variable (with the documented token fallbacks), and enables
one-time command reconciliation on READY. Starting this bot can therefore
change registered Discord commands. The generated `.env.example` also contains
legacy configuration placeholders; their presence does not mean the canonical
runner binds every field. Configure non-token settings explicitly through
`dcc_app_options_t` and `DCC_DEV_BOT_MAIN_WITH` as described in the
[Bot API](api/bot/main.md) and [App options](api/app/options.md).

For production, use `DCC_BOT_MAIN` or `DCC_BOT_MAIN_WITH` and deploy command
changes through an explicit reviewed `dcc_command_sync --plan` / `--apply`
step. Production Bot mode does not automatically load `.env` or sync on READY.

### Legacy Add Recipes Are Not Canonical 2.x Scaffolds

The `dcc_new_app add ...` recipes have not been ported to the installed
canonical 2.x API. Do not use them as the next step for the default scaffold.
For example, `add feature` can warn that main-file markers are missing and
emit `DCC_COMMAND_ARGS_IMPL` / `DCC_DEFINE_PUBLIC_FEATURE`, which require
non-installed legacy Sugar headers. Generated files may be written despite
those warnings; a successful tool exit does not establish build compatibility.

This limitation covers the legacy feature/command/subcommand, component,
autocomplete/event/view, config, action, task, message-command, middleware,
error-handler, latest-message, and preset recipes. They are retained for legacy
source workflows, not recommended installed-package examples. Add canonical
`dcc_listener_t` declarations and handlers manually using the
[listener API](api/app/listeners.md) and [Bot API](api/bot/main.md). This release
documents the limitation; it does not port the legacy add generator.

## dcc_hot_reload_host

Runs a Discord client and forwards bot logic to a hot reload module.

```sh
dcc_hot_reload_host --check
dcc_hot_reload_host --global
dcc_hot_reload_host --guild 123456789012345678
```

Important environment variables:

- `DCC_TOKEN` (`BOT_TOKEN` and `DISCORD_TOKEN` are accepted as fallbacks)
- `DCC_BOT_MODULE`
- `DCC_HOT_RELOAD_WORKER`
- `DCC_HOT_RELOAD_HEALTH_ADDRESS`
- `DCC_HOT_RELOAD_HEALTH_PORT`

## dcc_hot_reload_worker

Loads a bot module in an isolated worker process. It is normally launched by
`dcc_hot_reload_host`.

## dcc_command_sync

Plans or applies application command reconciliation.

```sh
dcc_command_sync --commands commands.json --application-id "$DCC_APPLICATION_ID" --plan
dcc_command_sync --commands commands.json --application-id "$DCC_APPLICATION_ID" --apply
dcc_command_sync --commands commands.json --application-id "$DCC_APPLICATION_ID" --guild "$DCC_COMMAND_GUILD_ID" --apply
```

Use `--remote remote.json` to compare against a captured remote fixture without
network access. `DCC_TOKEN`, `BOT_TOKEN`, or `DISCORD_TOKEN` are accepted for
REST writes. For projects generated by `dcc_new_app`, this CLI is optional
during development because `DCC_DEV_BOT_MAIN(...)` enables reconciliation
when the app starts. Production uses an explicit plan/apply deployment step.

## dcc_replay

Summarizes, validates, or replays captured Discord JSONL payloads.

```sh
dcc_replay --file events.jsonl --summary
dcc_replay --file events.jsonl --validate
dcc_replay --file events.jsonl --module ./bot.so --isolated
```

CI can require exact fixture contents with `--expect-records`,
`--expect-gateway`, and `--expect-interactions`. Validation rejects malformed
payload JSON and non-monotonic timestamps by default.

## dcc_doctor

Runs local, no-network installation and runtime diagnostics:

```sh
dcc_doctor
dcc_doctor --json
dcc_doctor --require-token --require-dave
```

It verifies the DCC compile/runtime version, LLAM 2.2.1+, LLAM ABI, OpenSSL,
token discovery without printing the token, certificate environment paths, and
the complete official libdave ABI. Token and DAVE absence are warnings unless
made required.

## dcc_interaction_webhook

Runs the shardless interaction webhook example with Discord Ed25519
verification.

```sh
dcc_interaction_webhook --check
```

Important environment variables:

- `DISCORD_PUBLIC_KEY`
- `DCC_INTERACTION_ADDRESS`
- `DCC_INTERACTION_PORT`
- `DCC_INTERACTION_PATH`
